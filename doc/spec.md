# オセロ局面到達手順復元アプリ 技術仕様書 v0.1

## 1. 概要

### 1.1 目的

8×8のオセロ盤面をユーザーが入力すると、標準初期局面からその盤面に到達するための**合法な着手列を1つ復元して表示する**Webアプリケーションを開発する。

例えばユーザーが終局盤面を入力した場合、アプリは以下を返す。

- 黒 C4
- 白 C3
- 黒 D3
- …
- 白 PASS
- 黒 H8

さらに各着手を盤面上で順番に再生し、「どの石が裏返ったか」まで確認できるものとする。

### 1.2 本システムが保証するもの

復元結果が `FOUND` の場合、

1. 標準初期局面から開始している
2. 各着手がその時点で合法である
3. パスは合法手が存在しない場合にのみ行われる
4. 出力された棋譜を最後まで再生すると入力盤面と完全一致する

ことを保証する。

一方、同一盤面へ複数の棋譜で到達できるため、「実際に過去に打たれた棋譜」を盤面のみから特定するものではない。

---

# 2. 対象ルール

World Othello Federationの標準ルールを基準とする。

黒が先手で、着手時には相手石を1枚以上挟んで反転させる必要がある。合法手が存在しない場合のみパスし、双方に合法手がなくなった時点でゲーム終了となる。citeturn379314search0turn670891search2

標準初期配置は以下。

- 黒: E4, D5
- 白: D4, E5

座標は左上を A1、右下を H8 とする。

---

# 3. 問題の数学的性質

このアプリの核心は、「盤面評価」ではなく**到達可能性問題（reachability problem）**である。

通常のオセロAIは、

> 現局面 → 将来局面

を探索する。

本システムでは逆に、

> 目標局面 → その1手前 → さらに1手前 → … → 初期局面

を探索する。

## 3.1 石数の重要な性質

オセロでは実際の着手1回につき、

- 空きマスに新しい石を1枚置く
- 既存の石はいくつか反転する
- 既存石が盤から消えることはない

という性質がある。

したがって盤上の石数を `N` とすると、その局面までに行われた実着手数は必ず

`N - 4`

回である。

例えば64マスすべて埋まった終局なら、

`64 - 4 = 60`

回の着手が存在する。

パスは盤面を変更しないため、この数字には含まれない。

この性質により、逆探索では1手戻るごとに必ず石数を1枚減らせる。

# 4. アルゴリズム方式比較

## 4.1 通常の順方向DFS/BFS

初期盤面から合法手を列挙し、目的盤面へ向かう方式。

### 長所

- 実装が単純
- 正しさが明確
- 既存のオセロエンジンを利用しやすい

### 短所

終盤盤面を対象にすると探索空間が極端に大きい。

60手近い棋譜を初手から総当たりする方式は実用的ではない。

### 判定

主方式として不採用。

ただし、序盤数手の到達状態を事前計算する用途には利用する。

---

## 4.2 逆向き探索

目標盤面から「直前の盤面候補」を生成して初期盤面へ戻る方式。

### 長所

- 最終盤面という強い制約を最初から利用できる
- 盤上の石数が毎回減る
- 最後に置かれた石の候補を限定できる
- 初期局面へ到達すれば、その経路自体が証明となる

### 短所

「どの石が最後に置かれたか」だけでなく、「どの石がその着手で裏返ったか」も逆算する必要がある。

一つの局面に多数の直前局面候補が存在する場合、指数的に探索量が増加する。

### 判定

**主アルゴリズムとして採用する。**

---

## 4.3 双方向探索

序盤側を順方向、終盤側を逆方向から探索して中間局面で接続する。

一般的な完全BFSはメモリ量が大きいため採用しない。

代わりに、

**序盤到達表 + 逆向きDFS**

という非対称な双方向方式を採用する。

---

## 4.4 SAT / SMT Solver

60手分の

- 盤面
- 手番
- 着手位置
- 反転位置
- パス

を制約として表現し、

「この最終盤面を満たす手順が存在するか」

というSAT/SMT問題として解かせる方式。

Z3は任意長のBitVectorを扱えるため、64bit盤面との相性がよい。citeturn379314search2turn379314search4

### 長所

- 数学的に明確
- UNSATになれば到達不能を証明可能
- アルゴリズム検証用に有用

### 短所

- 約60段階分の盤面遷移を制約化する必要がある
- オセロの8方向反転規則のモデルが大きくなる
- 局面による性能差が大きい
- 本番レスポンス時間を予測しにくい

### 判定

MVPの主アルゴリズムにはしない。

以下の用途に利用価値がある。

- 逆探索実装の正当性検証
- 小石数盤面のクロスチェック
- 将来的な「完全証明モード」

# 6. 盤面表現

Rust側では以下を基本形式とする。

```text
struct Board {
    black: u64,
    white: u64,
}
```

各bitが8×8盤面の1マスに対応する。

常に、

```text
black & white == 0
```

を満たす。

空きマスは、

```text
empty = !(black | white)
```

で算出する。

探索状態は、

```text
struct State {
    board: Board,
    side_to_move: Color,
}
```

とする。

`Color` は Black / White。

BitBoard方式を採用する理由は、

- 盤面コピーが高速
- 合法手生成が高速
- 反転処理が高速
- Hash計算が容易
- Rustの整数演算と相性が良い

ためである。

# 7. 通常の合法着手処理

以下の8方向を処理する。

- N
- NE
- E
- SE
- S
- SW
- W
- NW

着手位置 `x` について各方向を調べ、

```text
自石
↑
相手石 × 1枚以上
↑
新しく置く石 x
```

となっている方向をすべて反転する。

1方向以上で反転が発生した場合のみ合法手。

公式ルール上、着手によって挟まれた石はすべて反転させなければならない。citeturn379314search0

関数インターフェース例:

```text
legal_moves(board, player) -> u64

apply_move(
    board,
    player,
    square
) -> Result<MoveResult, IllegalMove>

MoveResult {
    board_after,
    flipped_mask
}
```

---

# 8. 「1手前の局面」の生成

本プロジェクトでもっとも重要な処理。

現在局面を `C`、

現在局面で次に打つ側を `q`

とする。

その直前に着手したプレイヤー `p` は、

```text
p = opposite(q)
```

となる。

## 8.1 最後に置かれた石候補

最後に置かれた石 `x` は現在、

必ず `p` 色でなければならない。

さらに標準初期配置4マス、

- D4
- E4
- D5
- E5

はゲーム中に新しく置かれるマスではないため、最後の着手候補から除外する。

---

# 9. 反転の逆算

ある候補 `x` から1方向を見る。

現在局面で、

```text
x P P P P ...
```

のように `p` 色の石が連続しているとする。

もし最後の着手でこの方向に3枚裏返したのであれば、1手前は、

```text
空 Q Q Q P
```

だったはずである。

そこで、

現在 `p` が連続している長さを `r`

とした場合、逆方向に戻す石数 `k` の候補は

```text
0
1
2
...
r - 1
```

となる。

`k >= 1` を選ぶ場合、その先にアンカーとなる `p` 石が必要なので `k < r` でなければならない。

8方向それぞれについて候補を作り、その直積を列挙する。

ただし、

```text
k1 = k2 = ... = k8 = 0
```

は合法着手ではないため除外する。

---

# 10. 最終的な前局面検証

逆算だけで前局面を確定しない。

候補盤面 `P` を作成後、

```text
apply_move(P, p, x)
```

を通常のオセロルールで再実行する。

結果が現在盤面 `C` と完全一致したものだけを正式な predecessor とする。

つまり、

```text
apply_move(P, p, x) == C
```

を必須条件とする。

これにより複雑な反転パターンについても、逆向きロジックにバグがなければ誤った棋譜を出力する可能性を大幅に抑えられる。

---

# 11. パスの逆算

パスは盤面を変更しない。

現在状態が、

```text
(Board, q)
```

の場合、その直前状態として

```text
(Board, opposite(q))
```

を考えられる。

ただし直前プレイヤーが合法的にパスできる条件は、

```text
legal_moves(Board, opposite(q)) == 0
```

かつ

```text
legal_moves(Board, q) != 0
```

である。

双方とも合法手がなければゲーム終了なので、そこでパスは発生しない。

この条件は公式ルールの「合法手がない場合のみ手番を失い、双方が打てなければ終了」に対応する。citeturn379314search0

---

# 12. 終局盤面からの探索開始

終局盤面では双方に合法手がないため、「次の手番」という概念は実質的に存在しない。

そのため探索開始時には、

```text
(target, BlackToMove)
(target, WhiteToMove)
```

の2状態を候補として探索する。

どちらかから標準初期局面へ到達できれば成功とする。

---

# 13. 探索

基本アルゴリズムはDFS。

```text
search(state):

    if state == STANDARD_INITIAL_STATE:
        return FOUND

    if state is in failed_states:
        return NOT_FOUND

    if opening_database contains state:
        join paths
        return FOUND

    predecessors = generate_predecessors(state)

    order(predecessors)

    for predecessor in predecessors:
        result = search(predecessor)

        if result == FOUND:
            save parent
            return FOUND

    failed_states.add(state)

    return NOT_FOUND
```

BFSではなくDFSを利用する理由は、必要なのが原則「合法経路1本」であり、BFSではメモリ使用量が急激に増えるためである。

---

# 14. Transposition Table

異なる逆算経路から同一局面へ到達するケースが大量に存在すると予想される。

探索済みで、

「この状態から初期盤面へ戻れなかった」

ことが確定した状態を保存する。

キー:

```text
black_bits
white_bits
side_to_move
```

完全証明モードでは、ハッシュ衝突によって正しい局面を探索から除外してはいけない。

したがって単一の64bit Zobrist Hashだけで状態同一性を判断せず、完全な盤面キーを保持する。

メモリ制限でキャッシュを破棄することは許容する。その場合、速度は低下するが正しさには影響しない。

---

# 15. 序盤到達テーブル

逆探索の最終目的を初期盤面そのものではなく、

「初期盤面からK手以内で到達可能な既知状態」

にする。

例として、

```text
K = 12 actual moves
```

程度からベンチマークを開始する。

事前処理で初期局面から順方向に全合法手を生成し、

```text
State -> 初期局面からの棋譜
```

を保存する。

逆探索がこのテーブル上の局面へ到達すれば、

```text
序盤テーブルの棋譜
+
逆探索で発見した棋譜
```

を連結して解とできる。

Kは固定仕様ではなく、実測結果を見て10～16手程度の範囲で調整する。

---

# 16. 盤面対称性

回転・鏡像によって同等になる局面を正規化し、探索状態数を削減する。

ただし標準初期盤面では90度回転等によって黒白配置が入れ替わる変換が存在する。

したがってMVPでは、標準初期盤面の黒白配置をそのまま保存する対称変換のみを安全に利用する。

具体的には4種類の対称変換でCanonical Stateを生成し、

```text
min(transformed_state)
```

をキャッシュキーとする。

解を復元するときは使用した変換を逆変換して着手座標を戻す。

---

# 17. 探索順序

探索の完全性を壊さない範囲で、前局面候補の探索順序を変更する。

候補ヒューリスティックとして以下を実験する。

- 逆反転パターン数が少ない候補
- 序盤DBに近い石数を優先
- 初期4マスの色配置との差
- predecessor側の合法手数
- 角・辺を含む候補
- 過去の成功探索で高頻度だった特徴

ヒューリスティックは候補を削除せず、あくまで順序変更だけに利用する。

これにより完全性を維持する。

将来的にはWTHOR等の実戦棋譜データを使い、「実戦で出現しやすい手」を先に探索することもできる。WOFではWTHORを大規模なオセロ棋譜データベースとして案内している。citeturn670891search5

---

# 18. 並列化

探索木の最上位数階層について候補を複数ワーカーに分割する。

RustではRayonなどのデータ並列ライブラリを利用可能。Rayonはparallel iteratorやwork-stealingベースの並列処理を提供している。citeturn873315search0turn873315search1

ただし細かすぎる単位で並列化すると、

- スレッド同期
- Transposition Table競合
- タスク生成

のオーバーヘッドが増える。

そのため、

```text
root
 ↓
depth 1～3程度まで分割
 ↓
各ワーカー内部はDFS
```

という方式を基本とする。

解を1件見つけた時点で他ワーカーへキャンセルフラグを送る。

# 19. 正しさ

## Soundness

ある前局面候補について必ず、

```text
apply_move(predecessor) == current
```

を確認する。

初期盤面まで到達した経路を順方向に再生し、最終盤面と一致することも最後に再検証する。

したがって `FOUND` で返した棋譜は必ず合法である。

## Completeness

以下をすべて列挙すれば逆探索は完全である。

- 最後に置かれた可能性のある全マス
- 8方向すべての反転長
- 合法なパス

さらに正しい前局面を枝刈りしない限り、探索空間を最後まで調べれば、

「この盤面へ標準初期局面から到達できない」

ことを証明できる。

---

# 20. 探索結果ステータス

非常に重要な仕様として、以下を区別する。

### FOUND

合法棋譜を発見。

### UNREACHABLE_PROVEN

完全探索が終了し、到達経路が存在しないことを確認。

### UNKNOWN_TIMEOUT

時間・ノード数・メモリなどの上限に到達。

「到達不能」とは表示してはいけない。

### INVALID_INPUT

入力自体が盤面として不正。

### CANCELLED

ユーザーが探索を停止。

これにより「探索できなかった」と「数学的に到達不能」を混同しない。

---

# 21. 初期入力チェック

探索前に高速チェックを行う。

## 必須

- マス数が64
- B/W/EMPTY以外がない
- BlackとWhiteが重複していない
- 石数4枚以上
- D4/E4/D5/E5が空いていない

最後の条件は、初期4石はゲーム中に盤から消えないためである。

## 終局モード

さらに、

```text
legal_moves(board, Black) == 0
AND
legal_moves(board, White) == 0
```

を確認する。

満たさなければ、

「この盤面は終局状態ではありません」

と表示する。

- Black to move

```text
FOUND

```

探索結果を別実装またはZ3で検証する。

}
```

```

# 26. サーバー側制限

探索問題は入力によって計算量が大きく変化するため、DoS対策が必要。

設定値として、

- 最大実行時間
- 最大探索ノード
- 最大メモリ
- 同時探索数
- ユーザー/IP単位の実行数

を持つ。

Quickモードで上限に到達した場合は、

```text
UNKNOWN_TIMEOUT
```

を返す。

# 27. テスト仕様

## 27.1 通常ルールUnit Test

- 横1方向反転
- 縦反転
- 斜め反転
- 複数方向同時反転
- 辺
- 角
- 非合法着手
- パス
- 終局

## 27.2 Reverse Move Unit Test

通常の合法手、

```text
P --move--> C
```

を生成した場合、

```text
generate_predecessors(C)
```

に必ず `P` が含まれること。

これは本プロジェクトで最重要のproperty testとする。

## 27.3 Random Game Test

ランダムな合法棋譜を大量生成。

1. 正方向でゲーム生成
2. 任意局面を保存
3. 復元エンジンへ入力
4. 棋譜を復元
5. 復元棋譜を再生
6. 同じ盤面になることを確認

元の棋譜と復元棋譜が一致する必要はない。

## 27.4 Unreachable Test

石数の少ない局面について完全列挙を行い、

到達可能状態集合に存在しない盤面をテストデータとして利用する。

`UNREACHABLE_PROVEN` が返ることを確認する。

## 27.5 Symmetry Test

対象盤面を合法な対称変換した場合、対応する棋譜へ変換可能であることを検証する。

# 30. 最大の技術リスク

## リスク1: 逆向き分岐数

最大の問題。

現在盤面の同色の連続列から多数の「元の反転枚数」が考えられるため、一手前候補が大量に発生する局面がある。

対策:

- Transposition Table
- 序盤DB
- move ordering
- symmetry
- parallelism

を段階的に導入する。

## リスク2: 到達不能証明

経路を1つ見つけるのと、経路が絶対存在しないことを証明するのでは必要計算量が大きく異なる。

UI/APIでは必ず、

```text
到達不能
```

と

```text
時間内には判定できなかった
```

を分ける。

## リスク3: 実際の棋譜との誤認

盤面から復元した棋譜は、過去に実際に打たれた棋譜とは限らない。

UIには、

**「この盤面に到達できる合法手順の一例です」**

と明示する。

# 33. 結論

この問題では、通常のオセロAIのような「最善手探索」ではなく、**局面の逆向き到達可能性探索**を行うべきである。

中核となる考え方は、

```text
目標盤面
 ↓
最後に置かれた石を仮定
 ↓
その着手で裏返った石を逆反転
 ↓
通常の着手処理を再実行して検証
 ↓
1手前の盤面
 ↓
繰り返し
 ↓
初期盤面
```

である。

主方式として

**BitBoard + Reverse DFS + Transposition Table + Opening Frontier**

を採用する。

SAT/SMTは主探索ではなく検証・証明系機能として使用する。

この構成であれば、まず正しいMVPを作り、その後ベンチマークを基に探索順序・並列化・序盤DBなどを順次強化できる。
